# Бизнес-процессы (BP)

> Полная карта поведения сервиса: акторы, статусы сущностей, каждый сценарий по шагам (happy path + краевые случаи), сквозные правила.
> Назначение: единый источник правды для логики. Из этого документа выводятся фичи и техническая спецификация.
> Связанные: [01-product-spec](docs/01-product-spec.md) · [03-business-and-finance](docs/03-business-and-finance.md) · [04-payments-agent-scheme](docs/04-payments-agent-scheme.md) · [06-merchant-rules](docs/06-merchant-rules.md) · [07-operations](docs/07-operations.md)

## 0. Сквозные правила (применяются ко всем процессам)

Эти решения зафиксированы и определяют логику всех сценариев ниже.

| # | Правило | Решение | Последствие для системы |
|---|---|---|---|
| R1 | **Оплата** | Покупатель **платит онлайн сразу при брони** (модель TGTG). Резерва без оплаты нет. | Нет статуса «забронировано, но не оплачено». Бокс уходит в продажу только после успешной оплаты. |
| R2 | **No-show** | Не пришёл в окно → **деньги остаются заведению**, покупателю **не возвращаются**. | Заказ переходит в `expired`, сплит уже исполнен, возврата нет. Правило раскрыто в оферте. |
| R3 | **Отмена брони покупателем** | **Отмены нет.** Купил — забирай. | Нет кнопки «отменить» у покупателя. Возврат возможен только через жалобу (R4) или отмену со стороны заведения (BP-11). |
| R4 | **Возврат по жалобе** | Только **через суперадмин** (основатель) после проверки фото. | Жалоба не запускает авто-возврат. Возврат — ручное действие в суперадмине. |
| R5 | **Агентская схема** | Деньги заведения идут транзитом через сплит, не оседают на счёте основателя. | Сумма бокса делится на платеже: доля заведения → его счёт, комиссия+сбор → счёт основателя. См. [04](docs/04-payments-agent-scheme.md). |
| R6 | **Только самовывоз** | Доставки нет. | Нет адреса доставки, нет курьеров. Выдача в точке заведения по коду. |
| R7 | **Свежесть** | В боксе — только продукция в пределах срока на момент выдачи. | Ответственность на заведении. Нарушение → страйк/деборд (BP-10). |

## 1. Акторы

| Актор | Где | Кратко |
|---|---|---|
| **Покупатель** | Клиентское приложение (мобайл) | Ищет, бронирует, оплачивает, забирает, оценивает, жалуется. |
| **Персонал заведения** | Приложение заведения, роль `staff` | Видит заказы на сегодня, подтверждает выдачу по коду. Без доступа к деньгам/настройкам. |
| **Владелец/менеджер заведения** | Приложение заведения / админ-веб, роль `owner`/`manager` | Создаёт боксы, расписание, видит статистику, профиль. |
| **Суперадмин (основатель)** | Веб-панель | Модерация заведений, ставки, жалобы, возвраты, страйки, метрики. |
| **Система** | Backend | Автостатусы, сплит-платёж, пуши, автозакрытие окон, авто-флаги. |
| **Платёжный провайдер** | Freedom Pay (внешний) | Принимает оплату, исполняет сплит, проводит возвраты. |

## 2. Статусы сущностей (жизненные циклы)

### 2.1 Заведение (Merchant)

```
draft ─► pending_review ─► active ─► suspended ─► active
                            │            │
                            │            └─► deboarded (терминальный)
                            └─► rejected (терминальный)
```

| Статус | Значение | Кто меняет |
|---|---|---|
| `draft` | заявка заполняется | заведение |
| `pending_review` | ждёт модерации | система (по сабмиту) |
| `active` | работает, может выставлять боксы | суперадмин |
| `suspended` | временно приостановлено (авто-флаг или 2-й страйк) | система / суперадмин |
| `rejected` | отказано на модерации | суперадмин |
| `deboarded` | отключено навсегда (3-й страйк / грубое нарушение) | суперадмин |

### 2.2 Бокс (Offer/Box)

```
scheduled ─► published ─► sold_out
   │            │
   │            └─► closed (окно прошло / снят вручную)
   └─► (наступило время) ─► published
```

| Статус | Значение |
|---|---|
| `scheduled` | создан по расписанию, ещё не активен |
| `published` | виден покупателям, есть остаток > 0 |
| `sold_out` | остаток = 0 (но окно ещё не прошло) |
| `closed` | окно выдачи прошло или владелец снял |

> `sold_out` ≠ `closed`: распроданный бокс может снова стать `published`, если владелец увеличит остаток до конца окна.

### 2.3 Заказ (Order) — ядро системы

```
                 ┌──► paid ──► picked_up (терминальный, успех)
created ─► (оплата)│
                 │   paid ──► expired (no-show, R2, терминальный)
                 │   paid ──► refunded (возврат по жалобе/отмене заведения, терминальный)
                 └──► payment_failed (терминальный, бокс возвращается в остаток)
```

| Статус | Значение | Переход |
|---|---|---|
| `created` | заказ создан, ждём подтверждения оплаты от провайдера | старт |
| `payment_failed` | оплата не прошла | бронь не состоялась, остаток бокса возвращается |
| `paid` | оплачено, сплит исполнен, выдан код | активный заказ |
| `picked_up` | персонал подтвердил выдачу по коду | успех |
| `expired` | окно прошло, покупатель не забрал (R2) | деньги у заведения |
| `refunded` | возврат проведён (BP-09 / BP-11) | деньги вернулись покупателю |

### 2.4 Жалоба (Complaint)

```
open ─► resolved_refund   (суперадмин одобрил возврат)
   └──► resolved_rejected (суперадмин отклонил)
```

## 3. Бизнес-процессы

Формат: **Триггер → Шаги (happy path) → Краевые случаи → Результат**.

---

### BP-01. Онбординг заведения

**Актор:** заведение + суперадмин. (Подробный оффлайн-чеклист — в [07-operations](docs/07-operations.md); здесь — то, что в системе.)

**Триггер:** заведение прошло продажи и готово подключиться.

**Шаги:**
1. Заведение регистрируется в приложении (телефон + OTP), заполняет профиль: название, адрес/гео, часы, фото, юр.данные (ИП/ТОО), счёт для сплита. → `draft`
2. Сабмит заявки. → `pending_review`
3. Суперадмин проверяет: регистрация, бизнес-счёт, подписан ли агентский договор. 
4. Суперадмин задаёт ставки заведению: `commission_pct` (10%), `service_fee_pct` (3%), `min_fee_per_box`.
5. Суперадмин одобряет. → `active`. Заведение может выставлять боксы.

**Краевые случаи:**
- Нет бизнес-счёта / не оформлено → `rejected` (фильтр воронки supply, см. [04](docs/04-payments-agent-scheme.md)).
- Ранний пилот без сплита (1–3 заведения): счёт для сплита не обязателен, выплаты вручную по акту — флаг `payout_mode = manual`.

**Результат:** активное заведение с настроенными ставками.

---

### BP-02. Регистрация / авторизация покупателя

**Актор:** покупатель.

**Триггер:** первый вход / повторный вход.

**Шаги:**
1. Ввод номера телефона.
2. Система шлёт OTP через WhatsApp (fallback — SMS).
3. Покупатель вводит код → создаётся/находится `User`, выдаётся сессия.
4. Запрос разрешения на геолокацию и пуши.

**Краевые случаи:**
- OTP не дошёл по WhatsApp → авто-fallback на SMS, кнопка «отправить снова» с таймером.
- Неверный код / истёк → повтор, лимит попыток (анти-брутфорс).
- Отказ от гео → главный экран по городу/последней точке, просьба включить гео для карты.

**Результат:** авторизованный покупатель.

---

### BP-03. Создание бокса заведением

**Актор:** владелец/менеджер.

**Триггер:** есть излишки на сегодня / плановое выставление.

**Шаги:**
1. «Создать бокс»: категория, цена, «ценность» (исходная стоимость), кол-во, окно самовывоза (с… до…).
2. Система проверяет правило цены: цена ≤ ⅓ ценности ([06](docs/06-merchant-rules.md)). 
3. Публикация. → `published`. Видно покупателям в районе.
4. **Главная рутинная фича:** «Повторить вчерашний» / шаблон — создание в 1 тап.
5. **Расписание:** автоматически выставлять бокс в заданные дни/время. → `scheduled` → авто-`published` в нужный момент.

**Краевые случаи:**
- Цена > ⅓ ценности → предупреждение/блок (правило настраивается).
- Заведение `suspended`/`deboarded` → создание боксов недоступно.
- Окно выдачи в прошлом → ошибка валидации.

**Результат:** активный бокс, доступный к брони.

---

### BP-04. Поиск и выбор бокса покупателем

**Актор:** покупатель.

**Триггер:** открыл приложение.

**Шаги:**
1. Главный экран: карта + список заведений рядом с активными боксами (`published`).
2. Фильтры: тип заведения, окно выдачи, цена.
3. Карточка бокса: фото, название, адрес, расстояние, категория содержимого («сюрприз»), цена + зачёркнутая ценность + % скидки, окно самовывоза, остаток, рейтинг заведения.
4. Кнопка «Открыть в 2GIS» (deep-link) для маршрута.

**Краевые случаи:**
- Нет боксов рядом → пустое состояние + предложение включить пуш «бокс рядом».
- Бокс распродан, пока смотрел → карточка показывает `sold_out`, кнопка брони неактивна.
- Окно бокса истекло во время просмотра → `closed`, скрывается из выдачи.

**Результат:** покупатель выбрал бокс.

---

### BP-05. Бронь и оплата (ядро, со сплитом)

**Актор:** покупатель + система + провайдер. **Правила:** R1, R5.

**Триггер:** нажал «Забронировать».

**Шаги (happy path):**
1. Выбор количества боксов (в пределах остатка).
2. Экран суммы: цена × кол-во + **сервисный сбор 3% раскрыт прозрачно** = итог к оплате.
3. Система резервирует остаток на время оплаты (короткий hold, чтобы не продать дважды).
4. Создаётся `Order` → `created`.
5. Оплата через провайдера: карта / Kaspi / Apple/Google Pay.
6. Провайдер исполняет **сплит** (R5):
   - доля заведения (цена − комиссия) → счёт заведения;
   - комиссия + сервисный сбор → счёт основателя;
   - эквайринг удерживается с основателя.
7. Подтверждение оплаты → `Order` = `paid`, остаток бокса уменьшается, генерируется **код выдачи + QR**.
8. Пуш покупателю: «бронь подтверждена», экран активного заказа с кодом.
9. Пуш/лента заведению: новый заказ.

**Краевые случаи:**
- **Оплата не прошла** → `payment_failed`, hold снят, остаток возвращён, покупателю «попробуйте снова».
- **Гонка за последний бокс:** два покупателя одновременно → hold (шаг 3) гарантирует, что второй получит `sold_out`.
- **Провайдер завис** (нет ответа) → заказ висит `created` с таймаутом; по таймауту hold снимается; идемпотентность по webhook’у провайдера, чтобы не задвоить.
- **Сбор «3%, мин. N ₸»** (опция из [03](docs/03-business-and-finance.md)): если 3% < мин., берётся минимум.
- **Ранний пилот без сплита** (`payout_mode = manual`): вся сумма на счёт основателя, заведению — вручную по акту.

**Результат:** оплаченный заказ `paid` с кодом выдачи.

---

### BP-06. Выдача бокса по коду / QR

**Актор:** персонал заведения + покупатель.

**Триггер:** покупатель пришёл в окно выдачи.

**Шаги:**
1. Персонал открывает «Заказы на сегодня» (по окнам выдачи).
2. Покупатель показывает код / QR из приложения.
3. Персонал вводит код или сканирует QR.
4. Система сверяет: код валиден, заказ `paid`, окно активно, бокс этого заведения.
5. Подтверждение → `Order` = `picked_up`. 
6. Пуш покупателю: «заказ выдан». Доступна оценка.

**Краевые случаи:**
- **Неверный код** → ошибка, заказ не закрывается.
- **Заказ уже `picked_up`** → «уже выдан», повторно нельзя (анти-двойная выдача).
- **Пришёл до начала окна** → предупреждение «окно ещё не открылось», выдача на усмотрение заведения.
- **Пришёл после окна** → заказ уже `expired` (R2); по умолчанию не выдаётся, на усмотрение заведения возможна выдача доброй волей (без возврата денег в любом случае).
- **Покупатель купил 2 бокса** → один код на заказ; выдаётся всё количество разом.
- **Нет интернета у персонала** → офлайн-ввод кода с последующей синхронизацией (v2; в MVP — требуется сеть).

**Результат:** `picked_up` — успешный цикл.

---

### BP-07. No-show (не пришёл)

**Актор:** система. **Правило:** R2, R3.

**Триггер:** окно выдачи закрылось, заказ остался `paid`.

**Шаги:**
1. Система по истечении окна переводит `paid` → `expired`.
2. Сплит уже исполнен на шаге оплаты → деньги остаются у заведения, основатель — со своей комиссией.
3. Возврата покупателю нет (раскрыто в оферте).
4. Пуш-напоминание покупателю **до** конца окна («не забудьте забрать») как профилактика.

**Краевые случаи:**
- Заведение по доброй воле всё же выдало после окна → может вручную отметить выдачу (опц.), деньги в любом случае у него.
- Массовые no-show у одного покупателя → флаг для антифрод (v2).

**Результат:** `expired`, деньги у заведения.

---

### BP-08. Оценка и жалоба

**Актор:** покупатель.

**Триггер:** заказ `picked_up`.

**Шаги:**
1. После выдачи — экран оценки (звёзды) + опционально текст.
2. Оценка обновляет публичный рейтинг заведения.
3. **Жалоба:** если проблема (плохой/просроченный/несоответствующий бокс) — «Пожаловаться» + **фото обязательно** + описание. → `Complaint` = `open`.
4. Жалоба моментально попадает в суперадмин.
5. Авто-флаг: всплеск низких оценок/жалоб за короткий срок → авто-`suspend` заведения до разбора (BP-10).

**Краевые случаи:**
- Жалоба без фото → не принимается (фото — обязательное доказательство).
- Жалоба после `expired` (не забирал, но жалуется) → суперадмин видит статус, обычно отклоняет.
- Оценка без жалобы → просто рейтинг.

**Результат:** оценка учтена; при проблеме — открыта жалоба, ждёт суперадмина (R4).

---

### BP-09. Возврат денег по жалобе

**Актор:** суперадмин + провайдер. **Правило:** R4.

**Триггер:** `Complaint` = `open`.

**Шаги:**
1. Суперадмин открывает жалобу: фото, описание, история заказа, рейтинг заведения.
2. Решение:
   - **Одобрить возврат:** инициирует возврат через провайдера. `Order` → `refunded`, `Complaint` → `resolved_refund`. Засчитывается страйк заведению (BP-10).
   - **Отклонить:** `Complaint` → `resolved_rejected`, денег не возвращаем.
3. Пуш покупателю о решении.
4. На старте политика щедрая (доверие важнее маржи — [06](docs/06-merchant-rules.md)).

**Краевые случаи:**
- **Возврат в сплит-схеме:** деньги уже ушли заведению → возврат откатывает и долю заведения (механику отката частичного сплита **уточнить у Freedom Pay** — открытый вопрос в [04](docs/04-payments-agent-scheme.md)). На раннем этапе при `payout_mode = manual` — проще (деньги ещё у основателя).
- Частичный возврат (купил 2, плох 1) — на усмотрение суперадмина.
- Абуз покупателем (систематические жалобы) → отклонение + флаг.

**Результат:** `refunded` либо `resolved_rejected`.

---

### BP-10. Страйки и деборд заведения

**Актор:** система + суперадмин. **Правило:** R7. (Политика — [06-merchant-rules](docs/06-merchant-rules.md).)

**Триггер:** подтверждённый инцидент (одобренная жалоба / проверка).

**Шаги:**
1. **Авто-флаг:** всплеск жалоб/низких оценок → авто-`suspend` (боксы скрыты) до разбора.
2. Суперадмин разбирает; при подтверждении — страйк:
   - 1-й → предупреждение (заведение остаётся `active`).
   - 2-й → временная приостановка (`suspended`).
   - 3-й → `deboarded` (отключение навсегда).
3. **Грубое нарушение** (просрочка/опасная еда) → немедленный `deboarded`, при необходимости уведомление контролирующих органов.

**Краевые случаи:**
- Активные заказы у `suspended`/`deboarded` заведения → уже оплаченные `paid` заказы должны быть выданы либо возвращены покупателям (см. BP-11).
- Ложный авто-флаг → суперадмин снимает `suspend`, возвращает `active`.

**Результат:** статус заведения обновлён согласно тяжести.

---

### BP-11. Заведение снимает/меняет бокс с активными бронями

**Актор:** владелец/менеджер + система.

**Триггер:** заведение хочет снять бокс или закрылось, но на него уже есть `paid` заказы.

**Шаги:**
1. Снять бокс без активных заказов → `closed`, ничего не происходит.
2. Снять/отменить бокс **с активными `paid` заказами** → система обязана **вернуть деньги** этим покупателям: `Order` → `refunded` (инициатор — заведение, не вина покупателя).
3. Пуш покупателям: «заведение отменило заказ, деньги возвращены».
4. Частая отмена с активными бронями → флаг качества (как анти-страйк со стороны заведения, v2).

**Краевые случаи:**
- Уменьшение остатка ниже числа проданных боксов — запрещено (нельзя «отозвать» проданное иначе как через возврат).
- Изменение окна выдачи после продаж → уведомить купивших; если неприемлемо — возврат.

**Результат:** конфликт «проданного» разрешается возвратом, а не потерей денег покупателя.

---

### BP-12. Настройка ставок per-merchant (суперадмин)

**Актор:** суперадмин.

**Триггер:** онбординг / пересмотр условий / крупная сеть.

**Шаги:**
1. В карточке заведения задать: `commission_pct`, `service_fee_pct`, `min_fee_per_box`.
2. Значения применяются к новым заказам **без передеплоя** (хранятся в БД).
3. Дефолт: 10% / 3% / мин. по [03](docs/03-business-and-finance.md).

**Краевые случаи:**
- Изменение ставок не затрагивает уже созданные заказы (суммы фиксируются на момент брони).
- Индивидуальные условия для сетей (tiered — v2).

**Результат:** гибкая экономика по каждому заведению.

---

### BP-13. Выплаты и сверка

**Актор:** система / суперадмин + провайдер. **Правило:** R5.

**Триггер:** проведённые оплаты.

**Шаги:**
1. **Режим `split` (основной):** доля заведения уходит ему **на каждом платеже автоматически**. Отдельная выплата не нужна. Основатель видит сверку: сколько ушло заведению, сколько комиссии/сбора получил.
2. **Режим `manual` (ранний пилот):** вся сумма у основателя; раз в неделю формируется акт и выплата заведению вручную; в суперадмине — отчёт «к выплате».
3. Возвраты (BP-09/11) учитываются в сверке.

**Краевые случаи:**
- Расхождение сплита и фактического зачисления → ручная сверка в суперадмине.
- Переход заведения `manual` → `split` после подтверждения гипотезы.

**Результат:** прозрачная сверка денег, чистый агентский статус.

---

### BP-14. Метрики и дашборд (суперадмин)

**Актор:** суперадмин.

**Триггер:** постоянный мониторинг.

**Содержит:**
- GMV, кол-во боксов, доход основателя (комиссия + сбор), эквайринг.
- Активные заведения, активные покупатели, retention, sell-through (% выкупа).
- Кол-во жалоб / 100 заказов, % возвратов, скорость возвратов.
- «Спасено еды» (кг/порции) — для PR/инвесторов.
- Время онбординга заведения, % активных заведений.

(Полный список метрик — [07-operations](docs/07-operations.md) и [09-go-to-market](docs/09-go-to-market.md).)

| Ситуация | Поведение системы | BP |
|---|---|---|
